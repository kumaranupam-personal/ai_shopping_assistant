## Eval suite

The cases are split into two sets in `backend/evals/sets/`: `dev.yaml` holds 40 cases and `holdout.yaml` holds 40 cases that were never used for tuning (see Dev and holdout sets). `backend/evals/run.py` runs one set against the real agent and the demo catalog in-process, without the HTTP layer. Cases depend on the demo catalog, so a change to the generator requires rerunning both sets. Both files use the same format, and each case contains:

- `id` and a one-line `description`.
- `turns`: an ordered list of user messages.
- `expect`: checks applied to the final turn. Every key is optional, and a case with none is unscored: it still counts toward grounding, latency and tokens, but not toward the pass rate.
  - `shown`: the conditions that every product in the final turn's last `show_products` call must meet, using the same `filters` syntax as `03-search.md`, and that call must show at least one product.
  - `min_shown`: the minimum number of products in that call.
  - `clarifies`: true when the final turn should make no `show_products` call and its reply should contain a question mark.
  - `declines`: true when the final turn should make no `search_products` or `show_products` call.
  - `mentions`: case-insensitive substrings the final reply must contain, such as a brand name the reply should name.
  - `reply_language`: `english` or `hinglish`. It is checked with a word-list heuristic: a reply counts as Hinglish when at least 2 distinct words from a fixed list of common Hindi words (such as hai, aur, ke, liye, yeh, aap, mein, sasta) appear in it.

Coverage of the dev set's first 20 cases, written before the split, each checking something the others don't:

- Every category in at least one case.
- 4 multi-turn refinements: a different attribute, a brand, an ordinal reference and a comparison.
- 2 vague requests that should get a clarifying question, one of them in Hinglish.
- 2 out-of-scope requests, one of them in Hinglish: an unrelated request and a category the store doesn't carry.
- 2 no-result requests that should trigger relaxation: one fixed by raising the budget, one by dropping an inferred attribute.
- 6 Hinglish cases, all scored: a single-turn intent, a refinement ("aur sasta dikhao"), an ordinal reference ("dusra wala"), an amount in Hindi number words ("teen hazaar tak"), a clarification and an out-of-scope request.

The dev set's other 20 cases and the 40 holdout cases come from one pool of 60, written without the prompt and split at random within each behavior, so the two sets share a distribution. `backend/evals/README.md` gives the holdout set's coverage and how the pool was written, checked and split.

The `expect` keys and the grounding check are rules, so they test what the agent did (filters, products, grounding, language), not how good its reply is. An LLM judge grades reply quality against the rubric under Judge rubric below (see Judge).

## Dev and holdout sets

The dev set is for finding failures and tuning the prompt and tools, so its scores show what the tuning fixed, not how the agent handles requests it wasn't tuned on. The holdout set measures that. The rules:

- Tune only on the dev set. Debugging single cases (`CASE_ID` arguments) works only on the dev set; the holdout set always runs in full.
- Write holdout cases from the specs, the catalog and real user phrasings, without reading the prompt, and change them only on purpose, in their own commit, which also updates the hash pinned in `tests/test_evals.py`.
- Run the holdout set only on a finished prompt version, as a plan recorded in the run log in `backend/evals/README.md` before the run sets out, and report the result as it comes out. Choosing between prompt versions by their holdout scores would turn it into a second dev set.
- If a holdout failure leads to a prompt or tool change, move that case to the dev set and write a new one in its place, and say so in the run log in `backend/evals/README.md`. Every holdout run goes in that log.
- No example in the system prompt or a tool definition may repeat an eval case's message or its expected result, such as a phrase from a case together with the filter value it should map to, because a case that passes by copying an example measures nothing. A test checks the quoted examples against the messages of both sets: they may share no pair of adjacent words, unless both are common words such as "for my", and no one-word example of 4 letters or more may be a word a case uses.

## Grounding check

The eval applies this to every turn of every case. A rupee amount is a number written after "₹", "Rs" or "Rs.", or before "rupees", with or without digit grouping, and a trailing "k" means thousands ("₹8k" counts as 8000). Each rupee amount in the assistant text must equal a `price` or `mrp` that appeared in a tool result during that conversation, a `price_min` or `price_max` in the `applied` filters a search reported (so a relaxed budget can be stated), or a number the user typed. User amounts are normalized before comparison, so "8k" counts as 8000, "5 hazaar" as 5000, and the Hindi number words one to ten followed by "hazaar" are recognized ("teen hazaar" counts as 3000). Each product ID or exact product title in the text must belong to a product returned by a tool in that conversation. Titles can repeat in a catalog, so a title counts as grounded when any product with that title was returned. Any mismatch counts as a grounding violation.

## Metrics and targets

The runner uses the provider named by `LLM_PROVIDER`. `--set dev` (the default) or `--set holdout` picks the set. It prints a summary and writes `evals/results/<set>/<timestamp>-<set>-<provider>-<prompt_version>.json`; dev runs from before the split are named without the set. The targets apply to each provider and set separately. Each results file records:

- `eval_set`, and `cases_sha256`: a SHA-256 hash of the case file, so a run can be matched to the exact cases it used (left out of dev runs from before the split);
- `catalog_sha256`: a SHA-256 hash of every product row in the catalog the run used, so the product IDs it stores can be checked against that catalog (left out of earlier runs);
- the provider and model;
- `prompt_version`: the first 12 hex characters of a SHA-256 hash of exactly what the model sees, the system prompt and every tool's name, description and schema, so any change to them gives a new version;
- `git_commit` and `git_dirty`: the commit the run used, and whether `backend/` had uncommitted changes outside `evals/results/` and `evals/prompts/`, so leftover run files don't count.

Each turn in a results file also records `tool_calls`: every tool call in order, with its arguments and its result (the tool's JSON, or the error message when it failed), so a reply can be judged against what the agent searched and got back (see Judge rubric). A search result keeps its product IDs as `ids` in place of the product rows, with `total_matches`, `applied` and `warnings`; whatever rebuilds the rows reads them from a catalog whose hash matches `catalog_sha256`, and refuses one that doesn't. Runs from before this was added don't have `tool_calls`.

The first run of a prompt version also saves its system prompt and tools as `evals/prompts/<prompt_version>.json`, so any two versions can be diffed. Each provider's reference run on the dev set is `evals/results/dev/baseline-<provider>.json`, in the same format as a run's file; it is replaced only on purpose, in its own commit. A baseline recorded before prompt versioning carries the version it ran with, marked `prompt_version_backfilled`, and no commit.

- Pass rate across scored cases: at least 90%. A case passes when every `expect` check holds and none of its turns has a grounding violation.
- Grounding violations: 0.
- Cache misses: 0, under the cache rule below.
- Turn latency, measured from the start of a turn to its end: p50 under 8 s and p95 under 15 s.
- Cost per turn and for the whole run, in USD, from the provider's `prices` (see `09-llm-providers.md`), is reported. It is left out when `prices` is unset. Cost has no target.
- Input and output tokens per turn, plus cache-read and cache-write tokens, are reported. From the second model call of a conversation onward, every call whose input (uncached, cache-read and cache-write tokens) is at least the provider's `min_cache_tokens` (see `09-llm-providers.md`) must read tokens from the cache, which confirms prompt caching works. Smaller calls aren't counted, because the provider can't cache them, and a provider that caches on a best-effort basis (no `min_cache_tokens`) isn't checked.

Every change to the prompt or the tools reruns the dev set on every registered provider, and every change to a provider's adapter or default model reruns it on that provider. The summaries go in the commit message. The holdout set isn't rerun for these changes (see Dev and holdout sets above).

## Judge rubric

The rubric, with decisions D1 to D8 below, was frozen for labeling. D9 was added after the first calibration round and before any held-out judging, and every change after labeling is listed with its reason.

The judge, and a person labeling replies for its calibration, grades one turn at a time against the criteria below. Each criterion gets **pass**, **fail** or **n/a**, with a one-line reason for every fail. A turn passes when every criterion that applies passes. The rubric grades only the current turn's reply, cards and suggestions; earlier turns are context, and a mistake in an earlier turn doesn't fail a later one.

What is graded for a turn: the earlier conversation, the user's message, the agent's tool calls with their inputs and results, the products shown (from the catalog), and the reply with its headline and suggestions. It never sees the agent's system prompt, the provider, the case or its expected result.

| Criterion | Applies when | Pass | Fail | From `04-agent.md` |
|---|---|---|---|---|
| **Relevance** | The turn shows products | Every shown product is a sensible candidate for the request: it meets the user's stated constraints, or the ones left after a relaxation the reply discloses, and doesn't clearly contradict the stated need or use | A shown product plainly doesn't fit the request (wrong kind of product, ignores a stated constraint, unsuited to the stated use when relevant products were among the results) | Rules 2, 4, 5 |
| **Helpfulness** | The turn shows products or answers a question | The reply gives the user something to decide with beyond what the cards show (a trade-off, a recommendation, what was relaxed), or directly answers every part of the question asked | The reply only restates what the cards show, is generic filler, or leaves part of the question unanswered | Rules 9, 10 |
| **Faithfulness** | The reply states any product fact | Every product fact (price, MRP, spec, attribute, rating, stock, availability, a comparison between products) is supported by a tool result in the conversation, and no amount is computed or rounded | Any fact unsupported by or contradicting the tool results; any invented discount, delivery date, stock level or product; any computed difference, total, saving, percentage or rounded amount | Rules 8, 11 |
| **Relaxation honesty** | The agent loosened a constraint the user gave or the agent inferred (it dropped a filter, raised the budget or dropped the size before showing results) | The reply says which constraint was loosened | The reply presents the results as if they met the original request | Rule 7 |
| **Clarification quality** | The reply asks the user a question instead of showing products | Exactly one short question, asked because neither a category nor a clear use case could be inferred, that would let the next turn search | More than one question; a question when a category or use case could be inferred; a question that wouldn't help narrow the search | Rule 3 |
| **Decline quality** | The agent declines the request | Polite and brief, says what it can't help with, and doesn't do any of the unrelated task | Does the unrelated task (fully or partly), lectures, is rude, or is so vague the user can't tell why | Rule 1 |
| **Language and style** | Every turn | Same language as the user's latest message (Hinglish or English), suggestions included; at most 2 sentences and 50 words (see D4); plain text; titles, brands and amounts as the tools returned them; no internal reasoning or commentary about the agent's own process | Any of these broken, such as a reply that explains which filters it inferred | Rules 10, 13 |

### Decisions

Examples here and in the judge's instructions are made up and match no eval case, so they can't decide a labeled row.

- **D1, a pick without a reason.** A reply that names a preferred product but gives no reason for it: helpfulness **pass**, because a recommendation helps the user choose; a reason is better but not required.
- **D2, opinion words.** Claims such as "good for long commutes" or "great for daily use": faithfulness **pass** when it's a reasonable reading of the product's attributes (a large battery for heavy use), and **fail** when the attributes contradict it or give no basis for it.
- **D3, specs used as a trade-off.** Rule 10 says not to repeat specs the cards show, but language and style **pass** when a spec is named to compare products or justify a recommendation ("the first has a bigger 30 L capacity, the second weighs less"), and **fail** when the reply only lists what the cards show.
- **D4, the length limit.** Up to 55 words **passes**, a tolerance of 5 words over rule 10's 50, and 56 or more is a **fail**. The 2-sentence limit has no tolerance: 3 or more sentences is a **fail**. Words are counted as text separated by spaces; a sentence ends with ".", "?" or "!", and a semicolon doesn't end one.
- **D5, replies without cards.** Answers to product questions and comparisons have no cards to carry the detail, but the same limit applies, as rule 10 states it for every reply.
- **D6, relevance after relaxation.** Products are judged against the request as relaxed, provided the reply discloses the relaxation (relaxation honesty covers the disclosure). Cotton kurtas shown for a rayon kurta request under a budget no rayon kurta meets is a relevance **pass** if the reply says so.
- **D7, a clarifying question with suggestions.** A question that also lists what the store sells ("Are you looking for clothes, electronics or kitchen items?"): clarification **pass**; it's still one question, and the options help the user answer.
- **D8, a decline that offers an alternative.** A decline that also suggests something the store does carry: decline **pass**, as long as it doesn't do the unrelated task and doesn't run a search in that turn.
- **D9, when faithfulness applies.** Added after the first calibration round, because labelers and the judge both split between pass and n/a on general claims: faithfulness applies whenever the reply says anything about the products or the results shown, including a general claim such as "all of these are under ₹2,000", and is n/a only when the reply mentions no product and no result.

## Labeling guide

Human labels calibrate the judge (`08-roadmap.md`, Phase 19): the judge is trusted only as far as it agrees with them. `backend/evals/labels/build_sheet.py` builds the labeling sheet and the recheck sheet from dev runs that store tool calls, rebuilding each shown product from the catalog; `labels/key/` holds what the sheets hide (`key.json`) and the hand-written breaks (`broken.json`).

- **Unit:** one row of the labeling sheet is one turn. Label every criterion in the rubric for it: pass, fail or n/a, with a short note for every fail and for any call that felt close.
- **Order:** read the user's message and the earlier conversation first, then the tool calls and the products, then the reply. Check faithfulness against the tool results and products in the row, not against memory.
- **n/a:** use it only when the criterion's "applies when" doesn't hold. If unsure whether it applies, label it and add a note.
- **Strictness:** apply the rubric and the decisions as written, not a personal standard. If a reply feels wrong for a reason the rubric doesn't cover, note it in the comment column; the rubric may need a new criterion, but the row's labels follow the current rubric.
- **No outside information:** label from what's in the row. The provider, the case and the rule-check result are deliberately left out and stay in the key file until labeling is finished, and some rows are deliberately broken copies of real replies.
- **Sittings:** label in two or three sittings of about 20 rows each, to avoid fatigue.
- **Consistency check:** after a break of at least a few hours, about a fifth of the rows, reshuffled, are labeled again on a second sheet, without looking at the first. A criterion on which the two sittings disagree often needs a clearer definition: fix the rubric, not just the labels, and record the change.
- **Holdout replies** are never labeled.

## Judge

`backend/evals/judge.py` is the judge. It renders a turn with `evals/turn_view.py`, the same code that fills the labeling sheet, and judges a sheet's rows by rendering them again from their source runs and breaks, so the earlier conversation lists every product shown in it with its details, where the sheet lists only titles, brands and prices. Its system prompt is short instructions, the catalog's brands by category, so a brand named in a message is recognized, and the Judge rubric section above with its decisions; it never contains the agent's system prompt. It answers through one tool call, `record_verdicts`, with two flat fields per criterion, a reason and then a verdict (`pass`, `fail` or `n/a`), so the verdict follows the reasoning and every provider returns the same structure; an answer without a valid call is retried once, then recorded as an error with each attempt's stop reason, tools and problems. It runs on `JUDGE_PROVIDER` with `JUDGE_MODEL` and `JUDGE_EFFORT` (see `01-architecture.md`), through the LLM layer in `09-llm-providers.md`, and its calls aren't traced. The judge version is the first 12 hex characters of a SHA-256 hash of its system prompt, tool schema, provider, model and effort, so any change to them gives a new version, and every judged file records it. One limit of what it sees: a search shows as its filters, match count and warnings, and only the products shown are listed, so a reply that names a product a search returned but didn't show can't be checked and may be failed on faithfulness.

- `uv run python -m evals.judge --results <results file>` judges every turn of a run that stores tool calls, after checking `catalog_sha256`, and writes `evals/results/<set>/judged/<results file name without .json>.judge-<version>.json`: each turn's verdicts and cost, and a summary with each criterion's pass rate over the turns it applies to, the share of turns that pass every criterion, the errors and the cost. `run.py --judge` does the same right after a dev run. A holdout run is judged only with `--holdout`, after a plan for it is recorded (see Dev and holdout sets).
- `--sheet calibration` or `--sheet held-out` judges the labeling sheet's rows of that split and writes `evals/labels/judged/<split>-judge-<version>.json`; `--retry-errors` judges again only the rows that ended in an error. The held-out rows are judged once, with the final judge version.
- `--agreement <judged sheet file>` compares the judge with the human labels: for each criterion, the rows compared, agreement, Cohen's kappa, false passes (the judge passed what the labeler failed), false fails and n/a mismatches, and how many deliberately broken rows had their broken criterion failed. Beside it, a "problem found" view counts pass and n/a as the same answer, since both mean the rater found no problem, and gives that agreement and its kappa. The same table is repeated for each provider's replies, so a judge that favours one provider's replies, such as its own provider's, shows as better agreement or fewer false fails on them. For calibration rows it also lists every disagreement with the judge's reason and the labeler's notes, which is what refines the judge's instructions; for held-out rows it prints the numbers only.
- `--consistency` compares the recheck sheet with the labeling sheet the same way, which measures the labeler's own consistency.
